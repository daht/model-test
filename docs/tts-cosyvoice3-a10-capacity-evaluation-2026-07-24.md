# CosyVoice 3 在 NVIDIA A10 上的 WebSocket 流式容量与瓶颈评估

日期：2026-07-24

对象：单张 NVIDIA A10 24 GB、`Fun-CosyVoice3-0.5B-2512`、真实 WebSocket PCM 流式输出

## 1. 执行摘要

本轮通过独立客户端访问公网 `WS → FastAPI → CosyVoice 3 → binary PCM` 完整链路，并把客户端逐请求结果与 A10 服务端 GPU、容器、GPU 进程和应用日志按时间对齐。

结论如下：

- **按当前临时交互 SLO，最大可持续容量为 0 RPS。** 最低的 `0.03 RPS` 开环档虽然没有持续排队，但 TTFA P95 为 3.282 秒、chunk gap P99 为 3.155 秒，已经分别超过 0.8 秒和 0.5 秒门槛。
- **当前混合短、中、长语料的无明显排队区约为 `≤ 0.03 RPS`。** 这只是 3 个正式请求的低负载观测点，不是生产承诺；`0.05 RPS` 已出现突发排队，`0.07 RPS` 的 TTFA P50/P95 恶化到 20.210/44.100 秒。
- **当前饱和音频吞吐约为 1.33–1.38 音频秒/墙钟秒。** 闭环并发从 1 增加到 4 时吞吐没有随并发增长，而 TTFA P50 从 3.117 秒升至 37.332 秒，说明新增请求主要在排队。
- **首要瓶颈是应用层全局推理锁造成的单请求串行执行，不是显存不足。** 锁覆盖完整生成器生命周期；有效负载窗口内 GPU 平均利用率 44.2%，显存峰值仅 5,253 MiB/23,028 MiB，无其他 GPU 进程、OOM 或重启。
- **第二瓶颈是模型流式块过大。** 服务日志中 181 个模型块的音频时长中位数为 4.00 秒、P95 为 4.36 秒。模型通常需要约 3 秒才能生成首个约 4 秒的音频块，因此即使没有排队，TTFA 和块间隔也无法满足交互式 SLO。
- 39 个正式请求全部成功，sequence、sample offset 和总样本数校验通过，播放模拟未断流。**“不断流”来自首个大块建立了约 4 秒缓冲，不代表首包延迟或流式粒度合格。**

因此当前实现可以作为功能验证环境，但不能声明具备满足交互式 SLO 的生产并发容量。应先解除串行化并缩小模型输出块，再重新寻找容量拐点和执行稳定性测试。

### 3.2 开环到达率

| 目标到达率 | 成功/请求 | 完成 RPS | 音频 RTFx | 平均在途 | TTFA P50/P95 | E2E P50/P95 | gap max | SLO |

`0.03 RPS` 档的平均在途仅 0.306，TTFA 仍约 3 秒，证明基础首包延迟并非排队造成。`0.05 RPS` 已出现 P95 8.431 秒的突发等待；`0.07 RPS` 的完成速率停在约 0.065 RPS，同时平均在途和 TTFA 显著增加，表现为到达速度开始超过当前串行服务速度。

开环每档样本数只有 3–8 个，因此这一轮足以定位瓶颈并否定当前 SLO，但不足以精确估计 P95/P99 或发布正式生产容量。

## 5. 瓶颈判定

### 5.1 主瓶颈：全局锁串行化

当前 `CosyVoiceTTSSynthesizer.stream_pcm()` 在进入模型前获取实例级 `Lock`，并在生成器全部结束后才释放。锁覆盖模型加载检查、`inference_zero_shot(..., stream=True)` 和所有音频块 yield，因此同一进程内只允许一个 utterance 执行模型推理。

```text
多个 WebSocket 已 accepted
          ↓
每个请求进入工作线程
          ↓
实例级 Lock 只放行一个 utterance
          ↓
其余请求等待上一段全部生成完成
          ↓
音频吞吐不随并发增长，TTFA 随队列增长
```

该判断由三类独立证据共同支持：

1. 代码明确把完整流式生成过程包在同一个锁内；
2. 闭环并发 1、2、4 的音频 RTFx稳定在 1.33–1.38，未出现并行吞吐收益；
3. 服务日志在多个 WebSocket 同时 accepted 后仍逐个记录 synthesis/yield 序列，没有并发模型执行；同时显存、容器 CPU 和 GPU 平均利用率均有明显余量。

因此删除锁本身并不自动等于安全并发。需要先确认 CosyVoice 模型对象、CUDA stream 和零样本音色缓存能否并发调用，再选择受控并发、微批调度或支持连续批处理的推理后端。

### 5.2 次瓶颈：流式块粒度约 4 秒

服务日志的模型块统计：

| 指标 | 结果 |
| --- | ---: |
| 音频块数 | 181 |
| 单块音频时长平均/P50/P95/最大 | 3.587 / 4.00 / 4.36 / 4.36 秒 |
| 单块模型 RTF 平均/P50/P95 | 0.788 / 0.710 / 1.097 |

模型 RTF 小于 1 表示生成速度快于播放速度，但一个典型 4 秒音频块仍需约 `4 × 0.71 ≈ 2.84` 秒才能产生。这与无排队请求约 3 秒的 TTFA、客户端约 3.2–3.6 秒的最大块间隔一致。

少数不足 1 秒的尾块会把单块 RTF 拉高，不能据此认定整段生成慢于实时。真正影响交互体验的是首块和后续块的绝对等待时间过长。

### 5.3 已排除或证据不足的方向

- **显存瓶颈：排除。** 峰值只使用 22.8% 物理显存，无 OOM。
- **其他 GPU 服务干扰：排除。** 全程仅一个 TTS Python GPU 进程。
- **容器崩溃或泄漏导致退化：排除本轮故障。** 无重启、OOM 或错误；本轮时长不足以评价长期内存泄漏。
- **网络是主瓶颈：不支持。** 网络会进入客户端 TTFA/E2E，但服务端日志显示约 3 秒的模型首块生成周期，且并发增长后的几十秒等待与串行队列一致。由于未单独保存 RTT，本轮不能量化网络的毫秒级贡献。
- **GPU 算力已经饱和：不支持。** 有效窗口平均利用率 44.2%，27.3% 样本为 0；局部 P95 达 100% 说明单次模型 kernel 会吃满 GPU，但调度存在明显空洞。

## 6. 当前容量边界

需要区分三个口径：

| 口径 | 本轮结论 |
| --- | --- |
| 满足临时交互 SLO 的容量 | **0 RPS**；最低档已因 TTFA 和 gap 失败 |
| 当前混合语料无明显排队区 | 约 `≤ 0.03 RPS`，仅为小样本方向性结果 |
| 串行实现的饱和音频吞吐 | 约 1.33–1.38 音频秒/墙钟秒 |

不能把闭环最高完成 RPS 0.092 当成生产容量：其 TTFA P95 已达 30.643 秒。也不能把零播放断流解释为低延迟；客户端是在等待约 3 秒后一次得到约 4 秒音频，随后生成速度略快于播放速度。

当前结果只适用于本轮短/中/长 1:1:1 语料。业务请求 RPS 与文本长度强相关，后续容量规划应同时使用音频秒/秒、输入字符/秒和真实业务长度分布。

## 7. 优化与复测顺序

1. **先增加服务端阶段指标。** 在 `task_finished.extra_info` 中真实填充 queue、model-first-chunk、synthesis 和 encode 时间，并暴露当前/最大队列深度，避免仅通过客户端 TTFA反推排队。
2. **验证受控并发执行。** 用并发 2 的最小实验确认同一模型实例是否线程安全、显存增量、结果一致性和吞吐收益；若不安全，不直接删除锁，改用明确的单卡调度器或支持批处理的后端。
3. **把模型输出块降到可交互范围。** 目标是 40–80 ms PCM 传输块，但传输层切块不能伪造模型首包；必须让模型或推理后端更早产出有效音频，并重新验证 `first_chunk_generated < synthesis_finished`。
4. **评估 CosyVoice 官方支持的高吞吐路径。** 对 vLLM、TensorRT 或其他后端分别记录精确版本，不能与当前 PyTorch 路径混成同一个结果。
5. **优化后重跑同一阶梯。** 先闭环 1/2/4/8 定位并行收益，再用开环到达率在最后通过点和首次失败点之间按 5%–10% 补档。
6. **候选容量点做 30–60 分钟 soak。** 使用每档至少 30 条且符合真实长度分布的语料，补充 WSS/TLS、音频质量、真实生产音色和 24 小时稳定性验证。

只有在最低负载先满足基础 TTFA/gap 后，提高并发才有容量意义。当前阶段不建议通过放宽 SLO 或增加等待队列来制造表面上的高并发数。

## 8. 适用边界

- 本报告是瓶颈定位和首轮容量扫描，不是生产容量验收。
- 开环档只有 3–8 个样本，P95/P99 统计不稳定；未执行边界补档和长时间 soak。
- 使用 WS，不包含 WSS/TLS、反向代理或生产负载均衡开销。
- 使用 CosyVoice 官方零样本参考音频，不代表最终生产音色的质量与性能。
- 未执行 MOS、ABX、发音准确率、音色相似度或长文本质量评估。
- 未测多实例、多进程、多卡、动态批处理和故障恢复。
- 客户端语料已按短/中/长交错，避免按长度分组造成阶段偏差；结果仍不替代真实业务长度分布。
